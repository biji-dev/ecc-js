# ECC JS fork (biji-dev/ecc-js): maintainer guide

This repository is a slim fork of [affaan-m/ECC](https://github.com/affaan-m/ECC).
It keeps only the technical, language-neutral surface that serves a
JavaScript/TypeScript, Bun, React, Next.js and React Native stack, and it still
takes upstream releases through a scripted merge.

- **What the fork contains, why, install and hooks:** [docs/ECC-JS.md](docs/ECC-JS.md).
- **This file:** how to maintain it (sync, review queue, releases, repo rules).

Everything upstream-authored keeps upstream prose. Fork documentation lives only
in fork-owned files (`FORK.md`, `docs/ECC-JS.md`, `.claude/rules/ecc-js-fork.md`)
and in the README banner rendered by `fork/bin/transforms/overlays.js`, so
upstream README/AGENTS edits merge without conflicts.

## How the fork is built

`fork/slim.json` drives everything:

| Key | Meaning |
| --- | --- |
| `<kind>.keep` / `<kind>.drop` | Kept items, and removed items with a reason code |
| `<kind>.pinned` | Kept items that block a sync if they disappear upstream (external projects call them by name) |
| `<kind>.own` | Your own `biji-*` items |
| `hooks.keep` / `hooks.drop` | Top-level hook entries kept in `hooks/hooks.json` |
| `mirrors` | Per-skill mirror dirs removed with a dropped skill (`.agents/skills/{name}`) |
| `paths.drop` / `paths.keep` | Repository trees removed or explicitly kept |
| `tests.drop` | Upstream tests removed with `triggeredBy`; an entry whose item triggers are all kept again stops applying and the test comes back |
| `requires` | Runtime couplings `verify.js` checks (for example continuous-learning-v2 for the hook root resolver) |
| `derived` | Files always regenerated from upstream; never hand-edit them |
| `queueHints` | Suggestions for new upstream items in the review queue |

Other fork state: `fork/state.json` (last synced upstream ref and tag, upstream
version, plugin build), `fork/review-queue.json` (undecided upstream items) and
`fork/install/*.json` (generated installer configs).

Every path falls into one of four classes during a sync:

1. **Dropped:** anything in the drop set (removed items and mirrors,
   `paths.drop`, active `tests.drop`, pending queue items and their coupled
   tests). Removed with `git rm`, even when upstream modified it.
2. **Derived:** `slim.derived` plus `package-lock.json` and `fork/install/*`.
   Reset to upstream, then regenerated by `fork/bin/transforms`.
3. **Merged content:** kept upstream files, including the fork's small patches
   (`scripts/lib/hook-flags.js` allowlist, `scripts/hooks/gateguard-fact-force.js`,
   `scripts/ecc.js`, `scripts/lib/install-manifests.js`,
   `workflows/orch-review.workflow.js`, `scripts/codex/*`, `.codex/AGENTS.md`,
   `mcp-configs/mcp-servers.json` and some tests). Merged 3-way by git with rerere.
4. **Fork-owned:** `fork/`, `tests/fork/`, `ecc/`, `FORK.md`, `docs/ECC-JS.md`,
   `.github/workflows/fork-*.yml`, `.claude/rules/ecc-js-fork.md` and every
   `biji-*` skill, agent, command and rule pack. Restored from the fork after
   every merge.

## One-time setup in a fresh clone

Upstream is fetched from the remote `ecc-upstream` (fetch-only). It is not named
`upstream` on purpose: `gh` and the GitHub UI would otherwise target
affaan-m/ECC. Always pass `-R biji-dev/ecc-js` to `gh`.

```bash
git remote add ecc-upstream https://github.com/affaan-m/ECC.git
git remote set-url --push ecc-upstream DISABLED
git config remote.ecc-upstream.tagOpt --no-tags
git config --replace-all remote.ecc-upstream.fetch '+refs/heads/main:refs/remotes/ecc-upstream/main'
git config --add remote.ecc-upstream.fetch '+refs/tags/v*:refs/tags/upstream/v*'
git config rerere.enabled true
git config merge.renameLimit 10000
gh repo set-default biji-dev/ecc-js
npm ci --ignore-scripts
```

## Syncing upstream

The weekly `fork-sync` workflow only forecasts. When upstream publishes a new
release tag (`vX.Y.Z`, no prereleases), it writes the forecast to the run
summary, uploads it as the `sync-forecast` artifact and opens or refreshes the
issue `upstream vX.Y.Z available`. The merge itself runs locally:

```bash
git switch main && git pull --ff-only
git switch -c sync/vX.Y.Z-$(date +%Y%m%d)
npm run fork:plan            # read-only forecast in fork/.sync-report.md
npm run fork:sync            # merge the newest release tag (or: node fork/bin/sync.js --ref vX.Y.Z)
# on MANUAL conflicts: resolve, git add, then
node fork/bin/sync.js --continue
npm test && node fork/bin/verify.js --drift --since main
git status                   # regenerated files, fork/state.json and the queue are already staged
git commit                   # merge commit: "chore(sync): merge upstream vX.Y.Z" (paste the report summary)
git push -u origin HEAD      # fork-ci runs on sync/** branches; wait for it to pass
gh run watch -R biji-dev/ecc-js "$(gh run list -R biji-dev/ecc-js --branch "$(git branch --show-current)" --workflow fork-ci --limit 1 --json databaseId --jq '.[0].databaseId')"
git switch main && git pull --ff-only
git merge --no-ff sync/vX.Y.Z-YYYYMMDD
git push origin main
git push origin --delete sync/vX.Y.Z-YYYYMMDD && git branch -d sync/vX.Y.Z-YYYYMMDD
gh issue close -R biji-dev/ecc-js <issue number>
```

Then update the harnesses (see Install in [docs/ECC-JS.md](docs/ECC-JS.md)) and
restart open sessions.

What the sync does automatically:

1. Refuses to start unless HEAD contains `origin/main`, the tree is clean and no
   merge is in progress.
2. Merges the upstream tag with a real merge commit.
3. Removes paths in the drop set, even when upstream modified them.
4. Resets derived files (README counts and banner, manifests, package.json,
   agent.yaml, hooks.json, plugin manifests, command registry) to upstream and
   regenerates them.
5. Restores fork-owned files from the fork.
6. Queues new upstream skills, agents, commands and rule packs in
   `fork/review-queue.json`, together with the upstream tests that reference
   them (`coupledTests`, removed while the item is pending). Tests of installer
   and hook code are never removed; they are listed as `blockingTests` and may
   fail until the item is decided.
7. Lists in `fork/.sync-report.md`: new top-level hook ids (removed until you add
   them to `hooks.keep` or `hooks.drop`), new dispatcher sub-hooks (off until
   allowlisted), new scripts, lib dirs and package bins, new top-level paths
   (shipped unless added to `paths.drop`) and security-relevant diffs to kept
   content (agent tools/model, hook commands, new process or network calls).
8. Sets the plugin build to 1 when the upstream version changes (otherwise adds
   1), renders `<upstream>-js.<build>` into every plugin manifest and stages
   every regenerated file.

Only files you edited that upstream also changed need manual resolution.

Exit codes of `fork:sync` and `fork:plan`:

| Code | Meaning |
| --- | --- |
| 0 | Success, or the tag is already merged |
| 1 | Error (dirty tree, HEAD behind origin/main, merge failure) |
| 2 | MANUAL conflicts remain: resolve, `git add`, then `--continue` |
| 3 | Blocked: kept items gone upstream, or upstream history diverged. The forecast report is written; `fork-sync.yml` treats this as a report, not a failure |

### Deciding review-queue items

Move each queued name into `keep` or `drop` (with a short reason) in
`fork/slim.json`, then:

```bash
npm run fork:apply     # prune decided entries, restore kept items and their tests, remove dropped, regenerate (staged)
npm run fork:bump      # new plugin version so harness caches update (staged)
npm test && node fork/bin/verify.js --drift --since origin/main
git add fork/slim.json && git commit
git push origin main   # or push a slim/<topic> branch, wait for fork-ci, then merge it --no-ff
```

If `fork:apply` fails, derived files are restored automatically, but item
removals and restorations stay staged. Fix the cause and rerun, or discard them
with `git restore --source=HEAD --staged --worktree -- <paths>` (keep your
`fork/slim.json` edit).

### Resolving a blocked sync

**Kept item gone upstream.** The "Kept items gone upstream" section of
`fork/.sync-report.md` lists each one with hints: an `R` line is a rename, a `D`
line is a deletion, and `successor (same name)` means the item moved to another
kind (for example a command that became a skill).

1. Remove the item from `<kind>.keep` (and `<kind>.pinned`).
2. If it was renamed or converted, add the successor to `keep` (and `pinned` if
   it was). If it was deleted, record it under `drop` with a reason such as
   `removed-upstream-vX.Y.Z`.
3. Commit the `fork/slim.json` change on the sync branch and rerun
   `npm run fork:sync`.

External consumers that reference a pinned `ecc:` name (task-runner skills,
project `CLAUDE.md` files) need the same rename.

**Hook id gone upstream.** A blocked `hooks:<id>` entry has no rename hints.
Compare `hooks/hooks.json` between `fork/state.json` `lastUpstreamRef` and the
target tag, remove the id from `hooks.keep`, add its replacement to `hooks.keep`
or record the old id under `hooks.drop`, update `ecc/setup.json` `hooks.allow`
if runtime ids changed, then rerun the sync.

**Upstream history diverged.** `lastUpstreamRef` is not an ancestor of the
target (a release-branch tag or a history rewrite). Nothing is merged; decide
by hand whether to merge the tag anyway and reset `fork/state.json` afterwards.

### Enabling or disabling a hook

Two layers: `fork/slim.json` `hooks.keep` decides which top-level entries stay in
`hooks/hooks.json`, and `ecc/setup.json` `hooks.allow` decides which runtime ids
actually run (dispatcher sub-hooks included). A hook needs both.

To enable one:

1. If it is a top-level entry in upstream `hooks/hooks.json`, move its id from
   `hooks.drop` to `hooks.keep` in `fork/slim.json`.
2. Add its runtime id (top-level or dispatcher sub-hook id) to
   `ecc/setup.json` `hooks.allow`.
3. `npm run fork:apply && npm run fork:bump`, run the tests and commit.

To disable one, reverse it: drop the runtime id from `hooks.allow`, and move a
top-level id from `hooks.keep` to `hooks.drop` with a reason. Same apply, bump,
test, commit. For a one-off or single project, `ECC_DISABLED_HOOKS` beats the
allowlist and needs no release — see "Hooks" in [docs/ECC-JS.md](docs/ECC-JS.md)
for the precedence order and the per-project settings example.

### Changing which items ship

Move a name between `keep` and `drop` (with a reason) in `fork/slim.json`, then
`npm run fork:apply && npm run fork:bump`, test and commit. Dropping an item also
removes its `.agents/skills` mirror and any `tests.drop` entry triggered by it;
keeping it again restores both. Drop a name out of `pinned` as well, or
`verify.js` fails on the missing pin.

### Your own skills, agents and commands

Prefix them with `biji-` so they never collide with upstream names, and list
them under `own` in `fork/slim.json`. `biji-*` paths are fork-owned, and own
skills are claimed by the `fork-own` install module automatically.

## Releases and versions

- Plugin version: `<upstreamVersion>-js.<pluginBuild>` in the five plugin
  manifests. `package.json` `version` and `VERSION` stay upstream's.
- Bump the build (`npm run fork:bump`) for every change that ships (skills,
  agents, commands, rules, hooks, scripts, `ecc/`, MCP configs, workflows,
  plugin manifests), or Claude Code, ZCode and Codex keep their cached copy.
  `verify.js` enforces this against a base ref: `--since <ref>` locally,
  `FORK_VERIFY_BASE` in fork-ci (previous main tip on push, PR base, or the
  merge-base with main on sync/slim branches).
- No tags. `fork/state.json` (`lastUpstreamTag`, `lastUpstreamRef`) and the
  `chore(sync): merge upstream vX.Y.Z` merge commits are the record of each
  sync. Never push the `upstream/v*` tags to origin (never `git push --tags`).

## CI

- `fork-ci.yml` (push to main, `sync/**`, `slim/**`; PRs to main): `npm test`,
  `node fork/bin/verify.js --drift` with the bump check, markdownlint and the
  workflow security validator.
- `fork-sync.yml` (weekly cron and manual dispatch): read-only forecast job, then
  an issue job that holds only `issues: write` and runs no repository code.

**Keeping the weekly forecast alive.** GitHub disables scheduled workflows after
60 days without repository activity, and upstream stable tags have been more
than 60 days apart. Check now and then:

```bash
gh api repos/biji-dev/ecc-js/actions/workflows/fork-sync.yml --jq .state   # expect "active"
gh workflow enable fork-sync.yml -R biji-dev/ecc-js                        # if disabled_inactivity
gh workflow run fork-sync.yml -R biji-dev/ecc-js                           # manual forecast
```

## Testing in this repository

- Use `npm test`. It sets `ECC_HOOK_ALLOWLIST=off`, because upstream hook tests
  expect profile gating, not the fork allowlist. For direct runs use
  `ECC_HOOK_ALLOWLIST=off node tests/run-all.js` or
  `ECC_HOOK_ALLOWLIST=off node tests/hooks/<file>.test.js`; without it about 5
  dispatcher and integration hook tests fail.
- Fork tooling tests live in `tests/fork/`; `node fork/bin/verify.js --drift`
  checks invariants and that derived files match the transforms.
- `CLAUDE.md` and `.claude/rules/node.md` are upstream text; the fork-specific
  rules for agents working here are in `.claude/rules/ecc-js-fork.md`.

## Upstream docs, security and support

- SECURITY.md, CONTRIBUTING.md, TROUBLESHOOTING.md, COMMANDS-QUICK-REF.md,
  docs/COMMAND-AGENT-MAP.md and the README body are upstream text and may name
  removed items. They stay unchanged so syncs merge cleanly.
- Report problems in fork-only code (`fork/**`, the hook allowlist and GateGuard
  patches, the fork workflows) at biji-dev/ecc-js. Problems in shared content go
  upstream per SECURITY.md.
- Fork-only changes follow this file, not CONTRIBUTING.md.

## Rules for this repository

- Merge `sync/*` and `slim/*` branches into main locally with
  `git merge --no-ff`. Squash and rebase merges are disabled on GitHub. Never use
  GitHub's **Sync fork** or **Discard commits** buttons: that breaks the
  upstream ancestry the sync depends on.
- Never hand-edit derived files; change `fork/slim.json` or `fork/bin/transforms`.
- Bump the plugin build for every change that ships.
- `.github/workflows` may contain only `fork-ci.yml` and `fork-sync.yml`
  (`fork/bin/verify.js` enforces this).
- Never push upstream `v*` tags to origin.
- The fork tooling and `npm test` assume a POSIX shell (macOS, Linux, CI on
  ubuntu-latest).
